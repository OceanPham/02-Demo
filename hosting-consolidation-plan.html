4.2 Domains at Hostinger, DNS at Cloudflare

Domain registration and DNS are separate: move registration/renewal to Hostinger while keeping Cloudflare nameservers for the Cadinvo domains. Move only dacu3d.nl DNS from Strato to Cloudflare.

  1. Export and compare DNS: save the Cloudflare zones for cadinvo.com/cadinvo.nl and all Strato records for dacu3d.nl. Add dacu3d.nl to Cloudflare and copy every required record, including Microsoft 365 mail and verification records.
  2. Prepare the transfer: obtain the dacu3d.nl code from Strato and the cadinvo.nl code from Hostnet. Confirm the managing account for cadinvo.com, unlock transfer and request its EPP/auth code. Allow for registrar processing time and approvals.
  3. Transfer registration to Hostinger: preserve existing Cloudflare nameservers for cadinvo.com and cadinvo.nl. Do not let the transfer replace them with Hostinger defaults. Keep Strato active until dacu3d.nl has moved safely.
  4. Move dacu3d.nl DNS to Cloudflare: compare the full zone first, coordinate DNSSEC/DS settings, then change nameservers. Check mail, website/redirects and Microsoft 365 domain status.
  5. Launch websites one domain at a time: keep the old destination until the replacement is approved, then point the web records at the VPS with Cloudflare Proxy enabled. Use a lower TTL where configurable ahead of the change; proxied records use Cloudflare's automatic TTL.
  6. Preserve redirects: keep cadinvo.nl and cadinvo.com redirecting to www.cadinvo.com through Cloudflare rules or the VPS behind Cloudflare. Validate HTTPS and every required redirect.
  7. Keep mail working: preserve MX, SPF, DKIM, autodiscover and verification records. Mail-related hosts remain DNS-only where required; the web proxy is for website/CRM traffic.

4.3 Email (recommended: stays on Microsoft 365)

  1. No mailbox moves. We copy the Microsoft records exactly: MX, SPF, DKIM (selector1/2._domainkey), autodiscover, enterpriseregistration, enterpriseenrollment and the MS= verification records.
  2. Add DMARC to all three domains: start in "report only" mode, monitor reports for about two weeks, and move to "quarantine" only after legitimate senders are verified. Monitoring continues during aftercare.
  3. Before cancelling Strato and Hostnet: log in to their webmail; if there are old mails you want to keep, we copy them into Microsoft 365 or export them.
If you still want mail at Hostinger (Hostinger Business Email): every mailbox must be moved, Teams/OneDrive/SharePoint stay at Microsoft anyway, and the CRM features that read and send Outlook mail and use OneDrive would have to be rebuilt. We do not recommend this.

4.4 All websites: codebase on the VPS

  1. Inventory every DaCu3D and Cadinvo website, starting with www.cadinvo.com on systeme.io: pages, assets, contact forms, mailing lists, newsletters, funnels, courses and payments. Export contacts and the list of page addresses.
  2. Confirmed: all websites use a codebase. Rebuild and deploy the websites on the Hostinger VPS. Keep the source in company-controlled Git repositories, with documented build and deployment steps. Shared components can be reused where useful.
  3. Agree the pages, content, design and owner before Day 1 (D2). Content updates go through the codebase; the handover must explain how to request and publish changes.
  4. Map each existing form and other systeme.io feature to its replacement. Include required integrations in the agreed scope and validate them using isolated sample data. Do not cancel a feature that has no working replacement.
  5. Preserve page addresses where possible; otherwise add permanent redirects. Check HTTPS, mobile layouts, metadata, analytics and forms before launch.
  6. systeme.io stays active until the replacement site and all required features are live and approved.
  7. dacu3d.nl: redirect to www.cadinvo.com, or publish its own codebase website/page (D4). cadinvo.nl keeps its redirect unless a separate website is agreed; any separate website also uses a codebase.

4.5 CRM (from Base44)

  1. Follows the separate CRM migration plan. New address, for example crm.cadinvo.com, created in Cloudflare DNS. Moving from Base44 includes replacing backend services, not just deploying the React frontend; the migration must be ready for rehearsal before this two-week rollout starts.
  2. Use KVM 2 for preparation in an environment isolated from production; promote it only after acceptance checks. If more resources are needed later, upgrade according to the provider's available options.
  3. Files (chat attachments, images, documents) on the VPS disk. Allow an estimated 3–6 GB of data on a 100 GB disk; confirm actual capacity before migration.
  4. Backups: database and files every night, encrypted, to a dedicated Microsoft 365 SharePoint/OneDrive folder (off-site, no new provider), plus Hostinger daily backups. We test a restore before go-live.
  5. Schedule cutover near the end of Week 2, after DNS and website checks pass, in a separate change window. If the Christmas–New Year preference is retained, choose Day 1 so the final cutover falls in that window. Keep Base44 available read-only for at least 2 weeks after cutover; agree and rehearse data reconciliation before any rollback.

4.6 CRM Chat, Evolution API and n8n

  1. CRM Chat is the intended conversation channel. WhatsApp chat inside the CRM is being phased out in favour of CRM Chat. Include Chat history, attachments, permissions and notifications in CRM migration checks.
  2. Evolution API is proposed for retirement. Exclude it from the planned VPS workload. Before decommissioning, confirm that no users or automations still depend on it and agree which WhatsApp history/attachments must be retained. Any remaining dependency is reviewed before stopping the service.
  3. n8n is a separate decision: confirm where it runs and which flows are still required. Move only the required automations to the VPS after checking resources and integrations.

4.7 Cloudflare and VPS protection

  1. Keep all three domains on Cloudflare DNS. Start by evaluating Cloudflare Free for Proxy, basic WAF rules and DDoS protection; confirm whether paid rules/support are needed.
  2. Route website/CRM traffic through Cloudflare Proxy. DNS-only web records do not receive proxy protection. Restrict direct origin web access to Cloudflare; Cloudflare Tunnel is an alternative where suitable. Limit management access to approved administrators.
  3. Use Full (strict) TLS with a valid origin certificate for the proxy setup. Keep CRM pages, authenticated responses and APIs out of shared caching. Validate login, CRM Chat/WebSockets, uploads and webhooks through the protection rules.
  4. Retain Hostinger's network-level DDoS protection: Cloudflare's web proxy does not cover every VPS port or attacks sent directly to its public IP. Severe attacks may still cause interruption.
  5. Enable two-factor access on company accounts, restore domain transfer locks after migration and coordinate DNSSEC settings. Document backup access and recovery ownership.

4.5 CRM (van Base44)

  1. Volgt het aparte CRM-migratieplan. Nieuw adres, bijvoorbeeld crm.cadinvo.com, aangemaakt in de DNS van Cloudflare. Verhuizen vanaf Base44 vraagt ook vervanging van backenddiensten, niet alleen deployment van de React-frontend; de migratie moet vóór deze uitrol van twee weken klaar zijn voor een proefmigratie.
  2. Gebruik KVM 2 voor voorbereiding in een van productie geïsoleerde omgeving; neem deze pas na acceptatiecontroles in productie. Breid later zo nodig uit volgens de mogelijkheden van de provider.
  3. Bestanden (chatbijlagen, afbeeldingen, documenten) op de VPS-schijf. Reken voorlopig op 3–6 GB data en een schijf van 100 GB; bevestig de werkelijke capaciteit vóór de migratie.
  4. Back-ups: database en bestanden elke nacht, versleuteld, naar een aparte SharePoint/OneDrive-map in Microsoft 365 (buiten Hostinger, geen nieuwe provider), plus de dagelijkse back-ups van Hostinger. Vóór de livegang testen we een herstel.

4.6 CRM Chat, Evolution API en n8n

  1. CRM Chat wordt het gesprekskanaal. WhatsApp-chat in het CRM wordt vervangen door CRM Chat. Neem chatgeschiedenis, bijlagen, rechten en meldingen op in de CRM-migratiecontroles.
  2. Evolution API wordt naar verwachting uitgefaseerd. Neem het niet op in de geplande VPS-belasting. Bevestig vóór uitschakeling dat gebruikers of automatiseringen er niet meer van afhankelijk zijn en spreek af welke WhatsApp-geschiedenis/bijlagen bewaard moeten blijven.   3. n8n is een aparte beslissing: bevestig waar het draait en welke flows nodig blijven. Verhuis alleen benodigde automatiseringen naar de VPS, na controle van capaciteit en integraties.

4.7 Cloudflare en VPS-beveiliging

  1. Behoud alle drie domeinen op Cloudflare DNS. Beoordeel eerst Cloudflare Free voor Proxy, basis-WAF-regels en DDoS-bescherming; bevestig of betaalde regels/support nodig zijn.
  2. Leid website-/CRM-verkeer via Cloudflare Proxy. DNS-only-webrecords krijgen geen proxybescherming. Beperk directe webtoegang tot de origin tot Cloudflare; Cloudflare Tunnel is waar passend een alternatief. Beperk beheer tot bevoegde beheerders.
  3. Gebruik Full (strict) TLS met een geldig origin-certificaat voor de proxy-opzet. Houd CRM-pagina's, ingelogde antwoorden en API's buiten gedeelde caching. Controleer login, CRM Chat/WebSockets, uploads en webhooks met de beveiligingsregels.
  4. Behoud Hostinger-netwerkbescherming tegen DDoS: de Cloudflare-webproxy dekt niet elke VPS-poort of directe aanvallen op het publieke IP. Zware aanvallen kunnen nog steeds onderbrekingen veroorzaken.
  5. Gebruik tweefactorauthenticatie op bedrijfsaccounts, herstel domeinverhuissloten na migratie en stem DNSSEC af. Leg reservetoegang en herstelverantwoordelijkheid vast.

4.2 Tên miền tại Hostinger, DNS tại Cloudflare

Tách đăng ký tên miền và quản lý DNS: chuyển đăng ký/gia hạn về Hostinger, giữ nameserver Cloudflare cho các tên miền Cadinvo. Chỉ chuyển DNS của dacu3d.nl từ Strato sang Cloudflare.

  1. Xuất và đối chiếu DNS: lưu zone Cloudflare của cadinvo.com/cadinvo.nl và mọi bản ghi Strato của dacu3d.nl. Thêm dacu3d.nl vào Cloudflare, sao chép đủ bản ghi cần thiết, gồm email và xác minh Microsoft 365.
  2. Chuẩn bị chuyển tên miền: lấy mã dacu3d.nl tại Strato, cadinvo.nl tại Hostnet. Xác nhận tài khoản quản lý cadinvo.com, gỡ khóa và lấy mã EPP/auth. Dự trù thời gian xử lý và phê duyệt của nhà đăng ký.
  3. Chuyển đăng ký về Hostinger: giữ nguyên nameserver Cloudflare của cadinvo.com và cadinvo.nl, tránh bị đổi sang nameserver mặc định của Hostinger. Giữ Strato hoạt động cho đến khi dacu3d.nl chuyển an toàn.
  4. Chuyển DNS dacu3d.nl sang Cloudflare: đối chiếu toàn bộ zone, phối hợp cấu hình DNSSEC/DS rồi mới đổi nameserver. Kiểm tra email, website/chuyển hướng và trạng thái tên miền trong Microsoft 365.
  5. Đưa website lên live từng tên miền: giữ đích cũ đến khi bản thay thế được duyệt, sau đó trỏ bản ghi web về VPS và bật Cloudflare Proxy. Hạ TTL trước nếu bản ghi cho phép; bản ghi proxied dùng TTL tự động của Cloudflare.

  2. Bổ sung DMARC cho cả ba tên miền: bắt đầu ở chế độ chỉ báo cáo, theo dõi báo cáo khoảng hai tuần; chỉ tăng lên quarantine sau khi xác nhận các nguồn gửi hợp lệ. Theo dõi này thuộc giai đoạn chăm sóc sau chuyển.
  3. Trước khi hủy Strato/Hostnet: kiểm tra webmail cũ; nếu có email cần giữ thì chuyển vào Microsoft 365 hoặc xuất lưu trữ.
Nếu vẫn muốn chuyển email sang Hostinger Business Email: phải di chuyển từng hộp thư, trong khi Teams/OneDrive/SharePoint vẫn cần Microsoft và các tích hợp CRM liên quan phải điều chỉnh. Không đề xuất hướng này.

4.4 Mọi website dùng codebase trên VPS

  1. Thống kê mọi website của DaCu3D và Cadinvo, bắt đầu với www.cadinvo.com trên systeme.io: trang, tài nguyên, form, danh sách mail, newsletter, funnel, khóa học và thanh toán. Xuất danh sách liên hệ và địa chỉ trang.
  2. Đã chốt: mọi website dùng codebase. Xây lại và triển khai trên Hostinger VPS. Mã nguồn nằm trong Git repository do doanh nghiệp quản lý, có hướng dẫn build/deploy; tái sử dụng component chung khi phù hợp.
  3. Chốt danh sách trang, nội dung, thiết kế và người phụ trách trước Ngày 1 (D2). Cập nhật nội dung qua codebase; bàn giao hướng dẫn yêu cầu thay đổi và xuất bản.
  4. Đối chiếu từng form và tính năng systeme.io với chức năng thay thế. Đưa tích hợp cần thiết vào phạm vi đã duyệt, kiểm tra bằng dữ liệu mẫu cách ly. Không hủy tính năng chưa có bản thay thế hoạt động.
  5. Giữ địa chỉ trang cũ nếu có thể, nếu đổi thì thêm chuyển hướng vĩnh viễn. Kiểm tra HTTPS, bố cục mobile, metadata, analytics và form trước khi lên live.
  6. Giữ systeme.io đến khi website và mọi chức năng cần thiết đã hoạt động, được nghiệm thu.
  7. dacu3d.nl: chuyển hướng tới www.cadinvo.com hoặc có website/trang riêng bằng codebase (D4). cadinvo.nl giữ chuyển hướng trừ khi thống nhất website riêng; website riêng cũng dùng codebase.

4.5 CRM — chuyển từ Base44

  1. Theo plan migration CRM riêng. Tạo địa chỉ mới, ví dụ crm.cadinvo.com, trong DNS Cloudflare. Chuyển khỏi Base44 cần thay thế cả backend, không chỉ deploy React frontend; bản migration phải sẵn sàng để chạy thử trước khi bắt đầu đợt triển khai hai tuần.
  2. Dùng KVM 2 làm môi trường chuẩn bị, tách biệt với production; chuyển sang vận hành chính thức sau khi kiểm tra đạt yêu cầu. Nếu cần thêm tài nguyên sau này thì nâng cấu hình theo khả năng của nhà cung cấp.
  3. Tệp đính kèm, ảnh và tài liệu lưu trên đĩa VPS. Dự trù dữ liệu 3–6 GB, đĩa 100 GB; xác nhận dung lượng thực tế trước khi chuyển.
  4. Sao lưu database và tệp mỗi đêm, mã hóa, lưu thêm vào thư mục SharePoint/OneDrive dành riêng trên Microsoft 365, kết hợp sao lưu Hostinger đã thống nhất. Kiểm tra khôi phục trước khi lên live.
  5. Chuyển CRM gần cuối Tuần 2, sau khi DNS và website ổn định, trong khung thay đổi riêng. Nếu giữ mong muốn chuyển dịp Giáng sinh–Năm mới thì chọn Ngày 1 phù hợp. Giữ Base44 chỉ đọc ít nhất hai tuần; thống nhất và diễn tập đối soát dữ liệu trước khi quay lại hệ thống cũ.

4.6 Chat của CRM, Evolution API và n8n

  1. Chat của CRM là kênh trao đổi dự kiến dùng chính. Đã và đang chuyển từ WhatsApp trong CRM sang Chat của CRM. Đưa lịch sử chat, tệp đính kèm, phân quyền và thông báo vào danh sách kiểm tra khi chuyển CRM.
  2. Dự kiến ngừng Evolution API. Không tính dịch vụ này vào tải VPS cần chuyển. Trước khi ngừng, xác nhận không còn người dùng hoặc automation phụ thuộc và thống nhất lịch sử WhatsApp/tệp cần lưu. Nếu còn phụ thuộc thì xử lý riêng trước khi dừng dịch vụ.
  3. n8n là quyết định riêng: xác nhận nơi đang host và các luồng còn cần dùng. Chỉ chuyển automation cần thiết về VPS sau khi kiểm tra tài nguyên và tích hợp.

4.7 Cloudflare và bảo vệ VPS

  1. Giữ DNS cả ba tên miền tại Cloudflare. Đánh giá Cloudflare Free trước cho Proxy, rule WAF cơ bản và chống DDoS; xác nhận có cần rule/hỗ trợ trả phí không.
  2. Đưa lưu lượng website/CRM qua Cloudflare Proxy. Bản ghi web DNS-only không nhận lớp bảo vệ proxy. Giới hạn truy cập web trực tiếp vào máy chủ gốc chỉ từ Cloudflare; có thể dùng Cloudflare Tunnel nếu phù hợp. Quyền quản trị chỉ dành cho quản trị viên được phép.
  3. Dùng TLS Full (strict) với chứng chỉ hợp lệ trên máy chủ gốc khi dùng proxy. Loại trang CRM, phản hồi đã đăng nhập và API khỏi cache dùng chung. Kiểm tra login, Chat/WebSocket, upload và webhook qua các rule bảo vệ.
  4. Giữ lớp chống DDoS ở mạng Hostinger: proxy web Cloudflare không bao phủ mọi cổng VPS hoặc tấn công thẳng vào IP công khai. Đợt tấn công nặng vẫn có thể gây gián đoạn.
  5. Bật xác thực hai bước cho tài khoản doanh nghiệp, khóa chuyển tên miền lại sau migration và phối hợp cấu hình DNSSEC. Bàn giao quyền truy cập dự phòng và người chịu trách nhiệm khôi phục.

Tài liệu kỹ thuật: Cloudflare Proxy · Origin protection · TLS · Hostinger Anti-DDoS
